# WB Studio — wbstudio.xyz

Multilingual (English / Arabic / German) portfolio website for **WB Studio**, the personal
architecture practice of **Wael Bousmael** — luxury private villas, interiors,
and spatial concepts in Jeddah, Saudi Arabia, and the Gulf.

Static site, hosted on **GitHub Pages** (custom domain via `CNAME`). No
framework, no dependencies — pages are generated by a single zero-dependency
Node script.

## How it works

```
data/projects.json      ← portfolio projects (bilingual) — EDIT THIS
data/site.mjs           ← all other site copy + config (bilingual) — EDIT THIS
data/locales.mjs        ← published language routes and page counterparts
scripts/build.mjs       ← generator: templates + sitemap
assets/css/site.css     ← the whole design system
assets/js/site.js       ← reveal animation, mobile menu, language memory
assets/js/contact.js    ← lead form (FormSubmit) + dormant Google Maps hook
assets/projects/<slug>/ ← images per project (cover.webp, gallery-NN.webp)
assets/projects/_incoming/  ← staging folder for your real work (see its README)
assets/licenses/LICENSES.md ← license register for every external asset
```

Generated output (do **not** edit by hand — files carry a banner comment):

- English is served directly at `/` for every visitor. There is no device,
  location, or saved-preference redirect. `/en/` remains an English homepage
  alias with its canonical URL pointing to `/`.
- Arabic home (RTL): `/ar/`. Existing Arabic deep links stay at `/work/`, `/work/<slug>/`,
  `/services/`, `/<landing-slug>/`, `/approach/`, `/journal/`,
  `/journal/<article-slug>/`, `/about/`, `/contact/`, `/credits/`
- English (LTR) deep links remain under `/en/...`.
- German (LTR): `/de/`, `/de/projekte/`, `/de/leistungen/`, `/de/ablauf/`,
  `/de/ueber-uns/`, `/de/kontakt/`, the studio’s own project presentations, two Berlin
  service pages, and credits. The two legal drafts are noindex and excluded from
  the sitemap while their publication details are reviewed.
- `sitemap.xml` with `hreflang` alternates

### SEO landing pages & journal (data-driven)

High-intent landing pages (e.g. `villa-design-jeddah`, `obhur-villa-design`)
live in the `landings` array in `data/site.mjs`; SEO guides live in the
`journal` array. Each is bilingual `{ ar, en }` and auto-generates its page,
nav/footer links, internal links, `sitemap.xml` entry, and schema:

- **landings** → `Service` + `FAQPage` + `BreadcrumbList` (each must target a
  *distinct* search intent — do not duplicate copy between pages).
- **journal** → `Article` + `BreadcrumbList`.

To add one, copy an existing entry in the relevant array, give it a unique
`slug`, write genuinely distinct bilingual copy, then run the build. Link new
landings to related projects via `relatedProjects` (project slugs) and to
sibling pages via `related` (landing slugs).

## Run / build

```bash
node scripts/build.mjs        # regenerate all pages + sitemap
python -m http.server 8123    # preview at http://localhost:8123
```

After adding or replacing images, run `python scripts/prepare-images.py`
(requires Pillow) before the build. It converts mislabeled or oversized WebP
sources, corrects project dimensions without reformatting the JSON, and writes
640px/960px derivatives plus `data/image-variants.json`. Correct any reported
dimensions in `data/site.mjs`. Existing source images within budget remain
unchanged; new variants preserve the source composition and never upscale.
Commit the manifest and derivatives with the sources and generated HTML.

Validation: `python scripts/verify-media.py`, `node scripts/verify-navigation.mjs`,
`node scripts/verify-locales.mjs`,
`node scripts/verify-aley-project.mjs`,
`node scripts/verify-seo.mjs`, `node scripts/verify.mjs`, and
`node scripts/check-reproducible-build.mjs`.
The media preparation command is only needed when images change; the regular
Node build remains dependency-free.

Requires only Node ≥ 18. GitHub Pages serves the committed HTML as-is; run the
build locally and commit the output.

## Add a project

1. Create `assets/projects/<slug>/` with `cover.webp` (~1800–2000px, 16:10) and
   `gallery-01.webp …` (~1400–1600px landscape / ~1100–1200px portrait).
2. Add an entry to `data/projects.json` (copy an existing one). Every text
   field needs both `ar` and `en`. Record real image `w`/`h` values.
3. If the images are not yours, add them to `assets/licenses/LICENSES.md`;
   if they are yours, set `"placeholder": false`.
4. `python scripts/prepare-images.py` → `node scripts/build.mjs` → review →
   commit (including responsive images, their manifest, and generated HTML).

## Remove / reorder projects

Delete (or move) the entry in `data/projects.json`, delete the image folder,
rebuild. Order on the Work page = array order. Homepage shows the first three
projects with `"featured": true`, with the first in the largest card.

## Replace placeholder images with your own

See `assets/projects/_incoming/README.md` — short version: drop your files in,
swap paths in `data/projects.json`, set `placeholder: false`, update
`LICENSES.md`, run `python scripts/prepare-images.py`, then rebuild.

## Language and market content rules

- English is the default homepage; Arabic has an explicit `/ar/` homepage.
- The header language menu links to the equivalent published page, or clearly
  labels a language-homepage fallback when no translation exists. All content
  is prerendered. Arabic/English legacy deep links remain unchanged.
- German content serves Berlin homeowners; Saudi service pages and guides remain
  in Arabic/English. Distinct Berlin/Jeddah services are not language alternates.
- Shared German copy is applied from the translation map in `data/site.mjs`;
  Berlin services and legal drafts are in `site.berlin`. Real-project translations
  are in `data/projects.json`. The build fails on missing rendered translations.
- Never hardcode visible text in `scripts/build.mjs` — put it in `data/site.mjs`
  or `data/projects.json` with fields for every published language.
- Stylesheet and script URLs carry deterministic content hashes to prevent
  stale assets after deployment; no extra frontend libraries are loaded.
- `.gitattributes` keeps browser scripts/styles in LF format so those content
  hashes stay identical across Windows and Linux Git checkouts.

## Measuring private villa inquiries

The footer's measurement preferences control optional, studio-run counts.
The existing browser scripts send allowed events to the Cloudflare Worker in
`measurement/worker.mjs`. Its `COUNTS` binding points to the private
`wbstudio-inquiries` D1 database, initialized with `measurement/schema.sql`.
Worker request logging is disabled. After opt-in the browser keeps only the
source channel and entry-page category for the tab. An accepted Arabic or
English inquiry can include the optional SAR project-budget band. Contact
details continue to go to the studio through the normal inquiry form.

To redeploy a collector change, upload `worker.mjs` and `metadata.json` as
the module and metadata parts of the Cloudflare Workers script upload for
`wbstudio-inquiries`. Keep its workers.dev endpoint enabled and preview URLs
disabled. Run `node --test scripts/verify-measurement-*.mjs` when changing
the browser events or collector. These tests require Node 22.13 or newer.

In Cloudflare D1 Studio, run either query for the last 30 Riyadh calendar days:

```sql
SELECT * FROM source_funnel_30d ORDER BY inquiries DESC, whatsapp_clicks DESC;
SELECT * FROM inquiry_budgets_30d ORDER BY inquiries DESC;
```

`country_group = 'SA'` means the connection was in Saudi Arabia. The budget
report covers project estimates selected by the owner. Contact clicks count
attempts to open a channel, and `inquiries` counts accepted form submissions.
Visitors who decline, block measurement, or signal GPC/DNT are excluded.
